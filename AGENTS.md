# defer-queue

A Claude Code mod (function-hook plugin) that holds the person's follow-up prompts while Claude works and sends them one per finished turn, the way omp's follow-up queue does. `README.md` is the user-facing spec; keep it in step with any behavior change in the same commit.

## Layout

- `hooks/policy.ts`: pure decisions and text: the queue's transitions (`/clear` reset, handback settlement, load, which record owns a change), the `/queue` grammar (`->`/`=>` shorthand, enumerated lists), what joins entries in the prompt box, first-line summaries. No `$`, no I/O. Unit-tested in `tests/policy.test.ts`.
- `hooks/register.tsx`: wiring. The `prompt.submit` hold, `turn.start`/`turn.complete` lifecycle, the release and its claim, `/queue` and `/defer`, `/clear` handback and the band above the prompt. Tested through the engine in `tests/defer.test.tsx`.
- `types/index.d.ts`: the queue's types and its `$.state` contract (`PluginState['defer-queue']`). Every `$.state` key the module uses must be declared here.
- `.claude-plugin/plugin.json`: manifest and `userConfig` options. `marketplace.json` makes the repo its own marketplace.
- `scripts/check.sh`: the commit gate (validate, test, typecheck).
- `scripts/drive.py`: the pty driver for the live interactive check (see Live checks).
- `.claude-plugin/types/` is generated by Claude Code when it loads the mod; it is gitignored. `tsconfig.json` is tracked here and extends it.

## Design invariants (this mod)

- **One state record.** The queue lives in one shaped atom (`queue`): `epoch`, `runningTurn`, `items` (oldest first), `claim` (the entry being released, with its token), `paused`, `recovery` (entries never sent automatically), `pending` (handbacks on their way to the prompt box, with the epoch they left in). Every change goes through `update`, whose updater stays free of side effects. No module-local flag decides delivery.
- **Main loop only.** `turn.start` and `turn.complete` with `e.agentId` set are ignored. A completion counts only when its `turnId` is the tracked `runningTurn`, and it is consumed once (the record clears `runningTurn` as it reads it).
- **One release at a time.** A release reserves `items[0]` as the `claim` in the same update that removes it, then submits without awaiting inside a hook. Nothing else is released while a claim stands. Success retires the matching claim; a drop or rejection hands the entry back (prompt box first, else the head of the queue with the queue paused) before the claim clears. A failed release never triggers another release.
- **/clear carry.** From `session.end` (clear, resume) the post-reset record lives in the module variable `carry`, and it is the queue's one current record: while `$.session.id()` is still the old id every change applies to it (mirrored into the old state), and once the id differs it is adopted into the new session's state (by `mergeCarry`) in the same update as the change. A `$.clock.after` timer started in `session.end` adopts it once the id has switched, trying every 100 ms for up to 10 s; `session.end` starts it when the reset begins and again when its awaited handback finishes, so a slow handback can't outlast it. Any access before that adopts it too. Every state access goes through `getQ`/`updQ`, one at a time (`serially`), so nothing reads or writes a half-adopted record; which record owns a change is `ownerOf` in `policy.ts`. The band shows the merge without writing. Only a reload before adoption loses the carry, however long that takes.
- **Admission is the boundary.** The mod's own `$.prompt.submit` runs through its `prompt.submit` hook when the engine admits it (live, 2.1.310: after a `/clear` typed while it waited). `$.prompt.submit` carries no id and a hook above may rewrite the text, so the module matches each admission to a release it submitted and hasn't seen admitted (`awaitingAdmission`, in order, preferring an exact text match), never by text alone. The hook admits it only while that release is the current epoch's claim (`admitsRelease`), else answers `{ drop }` and the entry stays in `recovery`; a refusal that hits a standing claim is finished by the release's settlement, so no claim outlives its submit.
- **Nothing lost, nothing resent by surprise.** A claim found after a hot reload (its callback died with the old module) moves to `recovery` marked "may already have been sent". `/clear` and a resume bump `epoch`, hand queued entries back to the prompt box, and move an unsettled claim or a failed handback to `recovery`. Recovery entries are shown and listed but never submitted by the mod.
- **No read-then-replace of the prompt box.** Handbacks `append` after whatever the box holds when the write lands (a read only picks the separator) and run one at a time through one chain. A `replace` based on an earlier read deleted live typing in review.
- **Handbacks are owned.** Take back, Take back all and the interrupt restore move entries from `items` to `pending` in one update, then write the box. The answer settles the entry by its id in whichever record owns the queue then (`settleHandback`), never a snapshot: filled, it leaves `pending`; refused, back to `items` with the pause they had (an interrupt pauses), unless the epoch moved, when they go to `recovery`. A reload moves `pending` to `recovery` (`abandonInFlight`).
- **Abort restores, errors hold.** A main turn that ends `aborted` puts every queued entry back in the prompt box, oldest first, after the draft, and sends nothing; if the box can't take them the queue pauses. An API error or refusal keeps them queued for the next answered turn.
- **Ingress.** Held: the person's own prompts (`composer`, `bridge`) typed mid-turn with `chat:queueSubmit` (or every mid-turn prompt with `defer_all_mid_turn`), anything that starts with `->`/`=>`, and `/queue`/`/defer` arguments. Never held: notifications, peers, schedules, other plugins, SDK prompts, slash commands, `!` lines, prompts with attachments. Queue input never overtakes older held work: while idle it joins the back and the oldest is sent.

## Commands

```sh
scripts/check.sh            # claude plugin validate . && claude plugin test . && typecheck
scripts/check.sh --no-tsc   # when TypeScript isn't available
```

All gates must pass before every commit. A behavior change needs a test in `tests/*.test.ts(x)` (the `claude-code/testing` kit: `mock.clock`, `mock.store`, `mock.env`, and `on(...)` hooks that stand for the engine beneath the plugin) written first and seen failing for the intended reason, then the change that makes it pass.

To try the mod in a live session: `claude --plugin-dir .` (interactive sessions hot-reload on save), or `claude -p --plugin-dir . "<prompt>"` for a headless run (always loads fresh; hooks that need a terminal won't fire). `claude --debug` logs every skipped hook and refused result. If defer-queue is also installed, disable the installed copy for the run (`--settings '{"enabledPlugins":{"defer-queue@defer-queue":false}}'`) so only the working copy loads.

## API reference

The API is early access and changes between releases; the declarations are the authority, not memory. Grep them by name (`'turn.step'`, `export type ToolCallResult`):

- after the engine has loaded this folder: `.claude-plugin/types/claude-code/index.d.ts`;
- otherwise the newest `claude-code.d.ts` the `plugin-authoring` skill writes under the temp dir (`scripts/check.sh` finds it), plus that skill's `reference.md` and `examples/`.

## Design invariants (apply to every mod built from the template)

- **Main conversation vs subagents.** Events from a subagent's loop carry `e.agentId` (`agent_id` on `classic.*` events). Decide explicitly whether the mod acts on subagents; by default return `next(e)` early for them.
- **Hot reloads reset module variables** (timers included). `register` and `session.start` run again; `$.state` and `$.store` survive. Anything that must persist goes in state or store. Change an atom's `shape` tag when its stored type changes.
- **Never throw out of a hook or timer for reporting.** Logging, status and toasts are best effort. A hook that guards (denies a tool call, drops a prompt) gets a `.catch` that decides fail-open or fail-closed deliberately (`next.called ? next(e) : { deny }`).
- **Headless sessions** (`e.isInteractive === false`, `claude -p`) have no terminal: no panes, `$.ui.notify` fails, `$.session.compact` rejects. Skip or degrade explicitly.
- **Cost and the prompt cache.** Anything that calls a model (`$.model.complete`, `classify`, `fork`, `$.agent.spawn`) is billed to the person. Say what it costs in the README, bound it with options, and don't change the system prompt or tool list per turn (that rewrites the whole prompt cache).

### Engine constraints found the hard way (Claude Code 2.1.29x–2.1.310)

- `$.prompt.submit` is refused from inside a `command.run` hook (it would wait on the turn the hook holds). Submit from a `$.clock.after(0, …)` timer.
- `$.session.compact` rejects while a turn runs and in headless sessions.
- A plugin's submitted prompt never expands `@` mentions; `$.prompt.fill` lets the person send it instead.
- `$.model.fork` replays the main thread's last request, which ends before the turn's final answer: quote the answer into the fork prompt if the fork needs it.
- The engine already prefixes `$.ui.status`, `$.ui.toast` and command output with the plugin name; don't add `defer-queue:` there. `$.ui.log` lines keep the prefix.
- A model `Write` outside the project raises a permission prompt; have the plugin write its own files with `$.fs.write` (it creates directories). `$.fs.write` replaces the whole file; there is no append.
- `turn.step` hooks are async generators in the path of every request: always pass the stream through (`yield* next({ ...e, effort })`). A rewritten `model` must be a full id (`claude-haiku-5-5`); an alias failed with `unrecognized_model`. Changing `effort` per request keeps the prompt cache (Opus, Sonnet, Haiku 5.5); changing `model` rereads everything uncached. The UI keeps showing the session's model and effort, so surface a rewrite with `$.ui.status`.
- `tool.call`: `const r = await next(e); return { ...r, context: [text] }` adds text the model reads after the tool result and the person never sees; `{ deny: reason }` blocks the call. A `tool.call` hook without `.catch` is reported by validate as a gate: give it one that fails open or closed on purpose.
- Haiku 5.5 rejects `temperature`/`top_p`/`top_k`, `budget_tokens` and assistant prefill with a 400. Prices step up 5x above 100K prompt tokens.
- Side calls (forks, completions, subagents, compaction) use the "everything else" prompt-cache bucket (5m on a subscription), not the main conversation's 1h one. Cache reads still count against plan usage.
- Text a hook injects for the model must not talk about the model's thinking or reasoning ("you can't see it", "doesn't count"): Opus 5.5's reasoning-extraction safeguard refused such a request. Phrase it in terms of the reply and the work.
- Don't build on instructions the model can ignore: a gate that "asks" the model to do something first failed live. Enforce in a hook, or give the model the information and let it decide.
- `/clear` is `session.end` with `reason: 'clear'` and no `session.start` after it: reset per-conversation state there.
- `$.state` is held per session id, and `/clear` starts a new one: live on 2.1.310 the plugin's state read empty (version 0) right after a `/clear`, while module variables lived on. defer-queue carries its epoch and Not sent list across in a module variable and merges it into the new session's state from a timer.
- A `$.clock.after(0, …)` timer started in `session.end` with `reason: 'clear'` fires in the new session (live, 2.1.310: about 20 ms later): `$.session.id()` there is the new id, the plugin's state already reads empty (its version kept counting), and a `$.state.set` made in it is what a later hook in the new conversation reads. The `prompt.change` with `kind: 'clear'` seen just before is the box emptied by submitting `/clear` (any submit raises one), not a reset signal, and no `session.start` follows.
- Subagent and teammate runs raise `turn.start` and `turn.complete` with `agentId` set (2.1.310); a main-loop tracker must filter both.
- A `prompt.submit` hook's `{ drop }` of a typed prompt leaves its text in the prompt box (live, 2.1.310, interactive; 0.1 had the same bug), so the next Enter sends it again. There is no write-if-unchanged fill, so clearing it would risk deleting newer typing: defer-queue leaves it and says so in the drop message.
### Bugs that recur in these mods (check every change against them)

Reviews of relay, defer-queue and prewalk kept finding the same family: a boolean flag left stale by a late event (track the running `turnId` instead), a message lost on a path nobody tested (a refused submit, a release racing a new hold), a timer or async step acting for a run that was cancelled or replaced (guard with a `runId` and re-check after every `await`), state that survived `/clear` or a reload when it shouldn't (or didn't when it should), and engine state copied into the mod's own flags (decide from facts at decision time). Two review rounds of blockers in the same mechanism means change the mechanism.

### Test kit notes

- A hook that answers an op on `$` (`command.register`, `fs.read`, `model.complete`, `ui.toast`, `session.messages`) returns `{ value }` or `{ deny }`; a hook that answers an event (`session.start`, `turn.start`, `turn.complete`) returns the event's result directly.
- One bottom hook per event per test file (a second registration errors). Test files with JSX are `.test.tsx`.
- Inline `plugins` load beneath the plugin under test while it is in the default `user` tier. To put one above it (a hook that rewrites before this mod's sees it), the file says `tier('append')` and the inline plugin `tier: 'prepend'`, as `tests/admission.test.tsx` does.
- Use `mock.clock(on)` and `clock.advance`/`settle` for time; there is no `setTimeout`.
- A throwing mock hook is skipped rather than surfacing its error, so test decisions that depend on an error's text as pure functions in `policy.ts`.
- Any helper that receives `$` must be a top-level function: the engine's static check refuses a module that passes `$` to a closure defined inside `register`. `atom({ plugin, key })` takes string literals, not a const.
- The kit accepted a wrong tool-input shape at runtime that `tsc` caught: run the typecheck.

### Live checks

The test kit stands in for the engine; it can't show what the engine really does. Before building on an engine behavior the types don't state, probe it: a throwaway observer mod (`--plugin-dir`) that logs events with `$.fs.write`, and one short live session, with `--model haiku` to keep it cheap. Record the Claude Code version a behavior was checked on. Headless runs (`claude -p`) create transcript folders under `~/.claude/projects/`; run them from a scratch directory.

Queueing needs a running turn and the `chat:queueSubmit` key, so its live check is interactive: `uv run python scripts/drive.py --help`.

## Conventions

- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`).
- Bump `version` in `plugin.json` for every release users should get. Installs from GitHub run a copy, and `claude plugin update` only replaces it when the version changes. An install whose marketplace is a local clone runs from the clone itself: edit, then `/reload-plugins`.
- MIT licensed: `LICENSE` at the root, and `plugin.json` says `MIT`.
- Treat the repo as public: no secrets, tokens, session IDs, personal paths or employer-specific details in code, tests, docs or commit messages.
- Don't add Claude or AI attribution trailers to commits.
